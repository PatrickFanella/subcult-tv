# Subsets 30-day campaign

Draft organic campaign. No launch date, publication, messages, paid budget, or scheduler is configured. A named owner chooses the start date and available weekly time. Initial suggestion: 3–5 hours per week and two channels, one owned social account and one relevant community with permission for project introductions.

## Objective

Learn whether people with local agent skill collections understand the group → preview → apply workflow, and where folder ownership becomes confusing. A successful campaign produces useful trials and specific feedback, not just impressions.

## Work plan

| Period | Work | Completion evidence | Decision |
| --- | --- | --- | --- |
| Week 1 | Run a disposable-fixture demo with the selected npm artifact; check install instructions and first-use wording; ask three willing testers to explain the preview | Package/version, terminal capture, task observations, and a list of confusing terms | Fix the first-use obstacle before increasing distribution |
| Week 2 | Publish an approved demo and one permitted community introduction; answer questions | Actual post links, observed actions if measurable, distinct feedback themes | Choose the useful message and record the time spent |
| Week 3 | Adapt the same source demo into a newsletter block and one preview-focused post | Source-to-derivative references and final media | Compare task-focused and collection-focused framing |
| Week 4 | Review feedback, errors, and available acquisition data | Dated readout with sample sizes and missing measures | Continue one channel, fix one workflow issue, and select the next experiment |

## Assets

- [ ] Product brief and current alpha installation block reviewed against the registry.
- [ ] Recorded fixture journey including ownership, preview, apply, verify, and rollback.
- [ ] One landscape and one square visual using the existing Personal Utility exports.
- [ ] Captions, legible terminal crop, final alt text, and source/permission records.
- [ ] Reviewed community introduction, social post, and newsletter block.
- [ ] Checked issue/support destination and owner available to answer replies.

## Measures

Use existing analytics and explicit tester feedback. No instrumentation is added by this packet.

| Measure | Definition | Limit |
| --- | --- | --- |
| Distribution reach | Platform-reported impressions and clicks for the dated post | Not product usage |
| Acquisition | Attributed website visits if existing analytics exposes them | Direct visits and cross-device paths may be unattributed |
| First-use success | Testers who correctly explain the preview and complete the fixture task / testers who attempted it | Small, self-selected sample; record instructions and assistance |
| Recovery understanding | Testers who can explain why later edits can block rollback / testers asked | Understanding question, not production recovery proof |
| Useful feedback | Distinct reports with task, expected result, actual result, and environment | Ask before quoting people publicly |

Keep a weekly log: date, owner, source asset, channel/post link, message variant, destination, available measures, participant count, issue, and next decision. Mark unavailable analytics explicitly. Set a numerical experiment threshold only after a baseline is observed. Do not infer token savings or agent quality from adoption or reach.

## Publication sequence

Recheck facts and artifact → owner reviews final copy/media → publish through the existing workflow → answer questions → review after 24–48 hours → record what to change. Pause promotion if installation or the chosen journey fails. A follow-up needs a real improvement or useful demonstration to show.
